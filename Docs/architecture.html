TranscriptKit architecture

TranscriptKit renders a streaming LLM conversation as one selectable document. Markdown arrives in chunks, is parsed incrementally, laid out with Core Text and drawn into a single view, so a selection can run from the first message to the last. Almost all of that work happens off the main thread: the main thread installs finished layouts and draws only what scrolls into view. The Markdown is CommonMark's blocks, nested in any order, plus GitHub's tables, task lists and strikethrough.

Main thread Parse queue (one per TranscriptStream) Layout queue (one per view) Render server (another process)

From a chunk to the screen

An app streams text with stream.append(chunk) and shows it with TranscriptText(stream:) in SwiftUI or a TranscriptTextView in UIKit. Each chunk crosses three threads before it reaches the screen, and only the last step happens on the main thread.

  1. Buffer. TranscriptStream.append appends to a string and unpauses a CADisplayLink. Hundreds of tiny chunks a second cost one string append each.
  2. Hand off once per frame. On each tick, whatever arrived is handed to the stream's serial parse queue, unless a parse is still running. When that parse finishes, more text schedules another tick, so the last chunk is never stranded.
  3. Parse. The incremental parser turns the new text into a new TranscriptDocument, numbered with a sequence. Registered views receive it on the parse queue, without going through the main thread.
  4. Lay out. The view's LayoutEngine keeps only the newest waiting document and lays it out at most once per display frame, reusing everything from the previous layout that did not change.
  5. Draw the tail. While text is being appended, the engine's TailRenderer draws the bottom 256 points of the document into one of a few IOSurfaces.
  6. Install. The finished layout and the drawn tail land in a mailbox. The main thread takes them in one go: it swaps in the layout, sets the tail layer's contents, moves the tiles' cutoff and reports a new height if there is one. That is one commit; nothing is drawn on the main thread.

The parts

Public API

  • TranscriptStream: append chunks, finish(), flush()
  • TranscriptText: SwiftUI view, from a stream or a document
  • TranscriptTextView: the UIKit view itself
  • MarkdownStreamParser, TranscriptDocument, TranscriptStyle
  • imageLoader on the view, or .imageLoader { } on TranscriptText (read once, when the view is made): off by default
  • TranscriptTag: the app's own inline tags and their TranscriptDecoration (colors, padding and shapes: .pill, .underline, or a TranscriptShapeRecipe; an animation: a TranscriptAnimationRecipe), given to the stream or parser
  • animatesTags on the view, or .animatesTags(_:) on TranscriptText: on by default, off with Reduce Motion
  • tagAnimationTiming and playTagAnimations() on the view, or .tagAnimationTiming(_:) and .playTagAnimations(trigger:) on TranscriptText: when animations play

Stream/ · iOS/ · Model/

Markdown

Block parser fed line by line: quotes and list items nest as a stack of containers around leaf blocks (paragraphs, ATX and setext headings, fenced and indented code, tables, rules), with task items, link reference definitions and hidden HTML comments; list items are numbered as CommonMark numbers them. Inline parser on UTF-16 with resumable checkpoints: emphasis, strikethrough, code spans, inline and reference links, images, angle-bracket and bare URLs and email addresses, escapes, numeric and all 2,125 named HTML entities, a few HTML tags, and the app's own tags with attributes.

MarkdownStreamParser · BlockParser · InlineParser

Model

A document is blocks of display text plus style spans, in one flat UTF-16 offset space with blocks joined by "\n". Each block records the quotes and list items it sits in and, on an item's first block, its marker. The document also keeps the link reference definitions, which reference links are resolved against. Finished blocks live in a SharedList that every version shares.

TranscriptDocument · TranscriptBlock · SharedList

Layout

Core Text line layout per block, stacked into a document layout with positions and offsets. Containers become indents, quote bars and markers; tables are typeset cell by cell; images get their space from a run delegate. Immutable once made, so it is built on one thread and read on another.

DocumentLayout · BlockLayout · TranscriptStyle · ImageStore · TagDecorations · TagAnimationPlayer

Engine

Per-view background layout with a latest-wins request slot, a per-frame cap, a merging mailbox, synchronous paths for the first layout and width changes, and the tail renderer.

LayoutEngine · TailRenderer

View

Draws settled text into 256-point tiles near the visible area, shows the tail layer, and answers every UITextInput query so the system's selection handles, loupe and edit menu work across the whole transcript.

Containers and leaf blocks

Quotes and list items nest in any order, as in CommonMark. The parser keeps the open ones as a stack and matches each new line against it, but what reaches the document is flat: one block per leaf, carrying the stack it sits in. Layout needs nothing more to draw the nesting.

  • Matching a line. A line first continues as many open containers as it can: ">" for a quote, enough indentation for a list item, where a blank line also counts. Containers it does not continue close, unless the line is a lazy continuation of a paragraph. Then new quotes and items open, and what is left is the leaf.
  • Tables. A one-line paragraph with a "|" becomes a header when the next line is a delimiter row with as many cells. Rows join until a blank line or another block starts. The block's text is the cells joined by tabs and the rows by newlines, so selection and copy treat it like any other block.
  • Images. An image is one U+FFFC character with an image span. Nothing is fetched unless the app sets an imageLoader, because an image URL written by a model can carry data out of the conversation in its address. Without one, or until the picture arrives, a chip shows the alt text.
  • References. A definition line ([label]: url) is never shown; the document keeps the first definition of each label. Text never depends on definitions, which usually come after the links that use them: [text][label] shows "text", and a shortcut [1] keeps its brackets. A reference span carries its label, is styled as a link once the label is defined, and is resolved when tapped. A new definition restyles the blocks that use it, wherever they are; the layout reports them as rectangles, and only those are redrawn, not everything below them.
  • Custom tags. An app defines tags such as <mark> or <mention id="42"> with TranscriptTag, each with a decoration: traits (bold, italic, monospaced, underline, strikethrough), a text color, a highlight behind the text, and a link, any of them worked out from the tag's attributes. The parser must know the tags, to tell <mark> from Array<Int>, so they are given to TranscriptStream or MarkdownStreamParser; any other tag shows as written. The decoration is worked out once, when the tag is parsed, and the span keeps the tag, its attributes and its decoration, so a document needs nothing else to be drawn. Colors carry a light and a dark value, because the tail is drawn off the main thread, where dynamic colors can't be resolved. A highlight is drawn behind the whole line's glyphs, one rounded rectangle across neighbouring runs, and stays inside the line, so redrawing a band of lines never cuts one. A decoration's link goes through the view's openLink, so tapping a mention reaches the app like any link.
  • Shapes around tagged text. A decoration can also draw shapes and ask for padding: a pill with a fill and an outline, an underline (solid, dashed, dotted, wavy, or a hand-drawn highlighter stroke), or the app's own shape, a TranscriptShapeRecipe that returns paths. Shapes are made when a line is laid out, on the layout queue, once per line the tag's text is on, and kept on the line; drawing only fills and strokes them, behind the text or over it. So the tiles and the tail draw the same pixels, recipes never run while drawing, and lines reused from the last layout keep their shapes. Each line's part of a tag gets its box, its font's metrics, whether the tag starts or ends there (a pill that wraps is open where it breaks), and a seed that is the same in every launch, for a hand-drawn look. Built-in shapes are measured along x from the fragment's start, so what is on screen stays put as the text grows. Padding is extra spacing on the character before the tag and on its last character, and a line that starts with a padded tag is moved over; the text itself is unchanged, so copy, selection offsets and accessibility are not affected. Shapes may reach 6 points above or below their line (the space between list items) and are clipped there; every place that decides what to redraw (the changed top, the tail's top and bottom, restyled blocks, the tiles) allows for that. Sideways they may reach 12 points past the text column on either side, so an app's own shape can start left of the text, as a highlighter band does where a wrapped line begins: the tiles and the tail are 24 points wider than the view and draw outside its frame, so the text never moves to make room. Each fragment says where its paths can be seen (visibleRect); the app leaves that much room around the view, as most layouts' padding does. All of a block's shapes behind the text are drawn before its text, so a pill never covers the line above. Only the tags on the lines laid out again are looked at: a streamed paragraph with a pill or a marker every few words costs 27 µs of layout per update on a Mac, against 19 µs for the same text without shapes.
  • Animated tags. A decoration can also have an animation, a TranscriptAnimationRecipe the app writes: from the tag's fragments, now with a box for each glyph, it returns curves over time for each glyph (offset, scale, rotation around an anchor) and paths to show (revealed from the left, faded in). TranscriptCurve has ramps with easing and a spring that leaves rest, reaches a peak and settles; nothing about a particular effect is built in. While a response streams, a tag with an animation shows its text but not its shapes; the parser marks its span as still waiting for its closing tag, and the closing changes the span, so its lines are laid out again with their shapes and with what the animation needs: each glyph's run, so it can be drawn alone. When a layout on the layout queue finds a tag that has closed since the last one, the engine starts its animation: from then on the tail is drawn without the tag's glyphs and shapes, and so are the tiles, which leave out the tag's glyph ranges by drawing parts of runs. The view asks the recipe for the animation when it installs that layout, draws each glyph and path once into a small image, on whole pixels, the way the tiles draw it, and puts the images on Core Animation layers above the text with the curves as keyframe animations; Core Animation plays them outside the app's process, so the main thread does nothing per frame while letters move. When the last curve ends, the tiles draw the tag again, with its shapes, in the same transaction as the layers go; if the tail had the tag's rows, the tiles take the tail back. At rest each image sits exactly where the tiles draw it: a test draws the text without the tag, adds the images, and gets the pixels of the text drawn whole, within 2 of 255 on each channel. Only tags that close while the view shows the text being appended are animated; text that is complete when it is shown is drawn at rest. By default an animation starts as soon as its tag closes, in the same layout that hides the tag. An app can make it wait (TranscriptAnimationTiming): until the tag is on screen, until the stream has finished, until the app calls playTagAnimations(), or any mix. A tag that has closed and waits is drawn as it was while open, its text without its shapes, in the tiles and in the tail; the view starts it when the last condition comes true (it looks again when the view scrolls, when a layout arrives, and when it is asked), and since the tail was drawn with the tag's glyphs, the tiles take the tail back if it holds the tag's rows. Streams now say when they have finished, even when finishing shows no new text, and a stream replaced by its finished document stays an append for the view: the engine merges the stream's last layout, if the view never took it, with the document's, and the view no longer sends the document it had before in between. A relayout (a new width, a new document), a change of appearance, Reduce Motion, or animatesTags off ends animations where they are. The chat sample's <hl> has a band that sweeps in under its text, line after line, while each letter jumps as the band reaches it and springs back.
  • API change. TranscriptBlock.Kind lost .quote and .listItem and gained .table. Blocks now have containers, outermost first, and a marker (bullet, number, or task) on an item's first block. Spans can have a reference and a customTag (kept out of line with the image, so a span is smaller than before), documents have linkDefinitions, and destination(of:) says where a span links to.

How the text is drawn

There is no text view or label underneath: every glyph is drawn with Core Text into layers the view owns. Two kinds of layer share the job, and a cutoff line decides which one draws what.

Tiles

  • Fixed 256-point bands of the document, each a CanvasView that draws its slice with DocumentLayout.draw.
  • Only tiles within half a screen of the visible area exist; others are hidden and reused, so memory stays flat however long the conversation is.
  • When something above the cutoff changes, only the band that changed is invalidated, and only lines intersecting it are drawn.

Tail

  • Starts at the last line when text begins arriving and stays put while the text fills it; it moves to the then-last line once the text comes within 48 points of its bottom.
  • Each frame redraws only the changed band into a CPU bitmap, on whole pixels, and copies just the changed rows into the next free surface (pool of up to four, never one the render server still holds).
  • Surfaces are tagged sRGB, like the bitmap, so colours match the tiles exactly.

One block through Core Text

  • Styles. Spans may overlap (bold inside a link), so each stretch between span boundaries gets the union of the spans over it. Text takes the context's fill colour, so light and dark mode need no relayout, only a redraw.
  • Blocks. Each container adds its indent. A quote's bar runs on through the gap into the next block in the same quote. A list item's marker (bullet, number or checkbox) sits in the gutter of the innermost item, on the first baseline. Code blocks get padding and a rounded background, rules a 1-point line.
  • Tables. Each cell is typeset on its own. Columns take the width of their widest cell; when the table does not fit, it is laid out as browsers lay out tables: every column gets at least its longest word, and the space left goes to the columns in proportion to how much more they want, so one long cell does not squeeze the others until their words break. While a table streams, rows that were already complete are not measured or typeset again and keep their lines while the columns stay the same, so only the row being written is redrawn. A row that widens a column lays out and redraws the whole table.
  • Drawn by hand. Core Text has no strikethrough, so strikethrough and underline are drawn per run after the glyphs. A picture is drawn into the space its run delegate reserved, and the U+FFFC glyph is skipped.
  • Lines reused. Line breaks are greedy, so text appended to a block can only change its last line. When a block is the previous block with text added at the end and the same styles, its earlier lines are carried over and Core Text starts again at the last line.
  • Offsets. Each line remembers the string offset it was typeset from, so caret positions and hit testing still work on lines typeset from a substring.

Parsing a stream incrementally

Every update has to look the same as parsing the whole text from scratch, and text already on screen must only grow at its end. The parser does work in proportion to the new text, not to what came before.

  • Lines. Each complete line goes through the block parser once. The unterminated last line is parsed on a copy of the state, because it may still turn out to be markup ("#", "-", "12.", a fence or a rule); such a line is held back until it is decided.
  • Frozen blocks. When a later block begins, the earlier one is parsed a final time and appended to the settled list. It is never looked at again.
  • Hold-back. Trailing * _ ~ ` \ [ ] ! and an unfinished entity such as &am or &#82 wait for the next character, and so do a partial HTML tag or comment. A custom tag is hidden until its ">" arrives, for up to 256 characters, past which it shows as written however it arrives; attributes must have values, so a word after a tag's name is decided by the next one. A "[" hides what follows it, for up to 64 characters, until the "]" and the character after it say whether it is a link, a reference or text, so neither a link nor a citation like "[1]" rewrites what was shown. An image shows nothing until its ")" arrives. A line that starts with "|" waits for the line below, which says whether it is a table header, and one that starts with "[" waits until it is clearly not a link definition. The word at the end of the decided text is parsed again with the next update, in case an "@" turns it into an email address. So text on screen almost never shrinks or changes style behind the reader. The known exceptions: a paragraph becomes a heading when the next line is "===" or "---"; a header row with no leading "|" shows as a paragraph until its delimiter row arrives; a bracket longer than 64 characters shows as written and loses its "[" if it turns out to be a link; and markup still unclosed when the stream finishes is shown literally. A link that turns blue when its URL or address completes, or its definition arrives, changes style only.
  • Settled result. The checkpoint also keeps the text, offsets and spans of everything that can no longer change, so an update builds only the text after it. The line being written is converted to UTF-16 a chunk at a time, and each complete line once. An open tag no longer holds the settled part back: its place in the text never changes, and its span is put in among the settled ones when the result is made. A paragraph streamed inside an unclosed tag went from 22.7 to 4.6 µs per append, against 3.8 µs for the same text without one. Under the test suite, debug builds rebuild the whole result as well and check that the two agree.
  • Cost. On a Mac in a release build, with two characters per append: 3.4 µs of work per append on the benchmark answer (4.0 µs on 15 November, before the Markdown additions, and 10.7 µs for the first, non-incremental parser), 4.4 µs on the second benchmark text, and 4.1 µs on a 3,900-character single-line paragraph (35.8 µs on 15 November, 469 µs at first). A 15,600-character line costs 9.1 µs: what is left grows with the paragraph through copying the block's style spans, the parser's state for it and its text on each update. On the iPhone 12 mini the parse queue is under 3% of the app's CPU while streaming. Just after the additions it was about 7%: their line scanning copied strings, and an older inefficiency, parsing an unfinished first line whole on every update, had become costlier with the richer inline parser. Both are fixed.

Sharing what stopped changing

Every frame produces a new document and a new layout, but almost all of both is the same as last frame. SharedList lets successive versions share one buffer and grow it without copying.

  • Documents. A TranscriptDocument is settled blocks (shared) plus one or two open blocks. Comparing two versions, or checking that one only appends to the other, looks at the open blocks only.
  • Layouts. A DocumentLayout carries the settled entries over untouched, lays out the open blocks, and can say where the first visible change is by comparing line identities, which tells the view which band to redraw.

What runs where

ThreadDoesNever does
Main Buffers appended text; installs a finished layout and tail in one commit; draws tiles when they scroll into view; answers every UITextInput query from the installed layout; lays out synchronously only for the first layout, for a new width or style, when an image loader is set, and when a picture arrives. Parse; lay out or draw the streaming text, apart from those synchronous layouts and one case: when a streaming table row widens a column, the table's part above the bottom strip is redrawn in tiles.
Parse queue Runs the incremental parser on what arrived in the last frame and passes each new document straight to the attached views. Touch UIKit or layouts.
Layout queue Lays out the newest document at most once per display frame; draws the tail into a surface; merges results that the main thread has not taken yet. Touch UIKit or a layer.
Loader task Runs the app's imageLoader in a detached task, once per image source, then asks the view to lay out again. Exist unless the app sets a loader.
Render server Composites tiles, the tail surface and the system's selection overlays. Run any TranscriptKit code.

Ordering is kept with sequence numbers and a source counter: a document from a stream the view has since detached from, or older than one already laid out, is dropped. Layouts are immutable, so the main thread reads one while the layout queue builds the next from it.

Selection and the system's text tools

  • One document to the system. The view adopts UITextInput and adds UITextInteraction(.nonEditable), so long-press, handles, the loupe, the edit menu and Copy are the system's own.
  • Flat offsets. Positions are UTF-16 offsets into all blocks joined by "\n", which is what lets one range span a heading, a list and a code block.
  • Stable while streaming. Every answer comes from the installed layout, which only changes when a new one is installed. Appends keep existing positions valid, so the view does not send textWillChange for them, which would cancel a drag in progress.
  • Copy. Copied text gets list markers, task boxes, quote prefixes, "---" for rules, tables as Markdown tables, images as their alt text and blank lines between blocks back, so it pastes as readable Markdown.
  • Links. A tap is a link tap only if a link glyph is under the finger; otherwise it goes to the selection gestures untouched. SwiftUI's openURL handles it.
  • SwiftUI. TranscriptText sizes to the proposed width; the view reports a new height only when the rounded height changes, a few times a second while streaming rather than per chunk.

Not there yet

  • Not parsed: maths, footnotes, raw HTML blocks other than comments, and definitions whose title continues on the next line. HTML tags outside the small set and the app's own show as text.
  • Custom tags are inline only. Decorations are worked out when text is parsed, so a finished document can't be re-themed without parsing it again. Attribute values are passed as written, without decoding entities.
  • Tag shapes, first version: left-to-right text only; a tag at the start of a table cell gets no room on its left (it reaches into the cell's padding); a caret or selection at a padded tag's edge sits inside its padding; padding before a tag goes on the character before it, so if that character is not a space and sits at the very end of a line, opening the tag can move it to the next line. The plain background highlight is still drawn separately from shapes.
  • Tag animations, first version: glyphs and paths only (no blur, no colour changes within a glyph, no layer filters), drawn above the text and not cut off, so a big movement covers what is around the view; the recipe runs on the main thread when the animation starts; an animation that ends while its rows are in the tail makes the tiles take the tail back early, and the tiles antialias a few edge pixels a little differently from the tail (seen as up to 55 of 255 on a few hundred pixels in a simulator recording); a tag's underline, strikethrough and highlight stay where they are while its glyphs move; if the next character arrives right after the tag and kerns with its last letter (a "." after a "y"), the static shape drawn when the animation ends can be a fraction of a point shorter or longer than the animated one. On an iPhone 12 mini (Release build, 20 traced launches), the animation's frames render as fast as the ones around it (all under a frame), but because Core Animation renders every frame for its 1.65 s, about one animated frame in a hundred misses its deadline, as any animation that long would; starting one takes about 0.9 ms (3 to 4 ms in the app, cold) on the main thread. Its layers use no masks (a band's reveal clips to the layer's own bounds) and go to the screen in the same commit as the tiles that stop drawing the tag.
  • Reference links differ from CommonMark, and from Apple's own parser, in two ways, both so that text never changes after it is shown: an undefined [text][label] shows "text" rather than the source, and a shortcut reference keeps its brackets ("[1]" rather than "1").
  • A new link definition makes the next layout look at every block once, to find the references it restyles.
  • Each update still copies the open block's style spans, the parser's state for it and its text, so the parser's cost per update grows slightly with the paragraph: 7.9 µs per append on a 15,600-character line on a Mac, against 3.5 µs on ordinary answers. Layout adds about 26 µs per frame for a 3,900-character paragraph.
  • A picture arriving, or setting the image loader, lays the document out again on the main thread, and that layout looks at every block once.
  • A table row that widens a column lays out the whole table again, and the part of it above the bottom strip is redrawn on the main thread on that frame.
  • Text on screen can still change behind the reader in a few cases: a "===" or "---" underline that makes a heading, a table header with no leading "|", a bracket longer than 64 characters that turns out to be a link, and unclosed markup when the stream finishes.
  • Tables, task boxes and image chips have not been checked in dark mode. The checked box is a fixed blue with a white tick.
  • No VoiceOver support yet: the view exposes no accessibility elements.
  • Opening a long conversation and rotating lay out the whole document synchronously on the main thread: about 160 ms for 200 messages on the iPhone 12 mini.
  • Streamed text updates at most 60 times a second, also on 120 Hz screens, where scrolling still runs at the full rate. On an iPhone 17 Pro at 120 Hz, TranscriptKit dropped no frames while streaming or scrolling.
  • The tail costs 6 to 8% more CPU in total and 8 to 13 MB of peak memory while text streams.
